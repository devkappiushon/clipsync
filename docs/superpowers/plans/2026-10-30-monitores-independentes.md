# Monitores independentes: plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar o mapa por monitor e a travessia A → notebook → B, inversa e pelo lado de entrada, com mouse físico do desktop Windows e receptor GNOME Wayland de uma tela.

**Architecture:** Identidades privadas persistem separadamente do mapa. Um compilador Rust produz a geometria efetiva que a prévia, a transação de aplicação e as sessões v4 compartilham. O agente aplica o mapa sob lock cooperativo, invalida sessões antes da escrita e conserva uma tabela imutável de retorno por sessão; a interface edita somente rascunhos até a confirmação.

**Tech Stack:** Rust do workspace, serde/TOML/postcard, Tokio, ashpd/reis, adaptadores Win32 existentes, Tauri 2 e JavaScript ES modules sem framework novo.

**Spec:** `docs/superpowers/specs/2026-10-30-monitores-independentes-design.md`, aprovado por João conforme instrução do Maestro. O Maestro sincroniza a marcação de aprovação do documento e o adendo do contrato antes da implementação.

## Restrições globais

- “Um monitor nunca vira outro peer.” Nenhuma criação de cartão, aplicação, oferta ou retorno concede `input_in`.
- “A migração do layout só ocorre ao aplicar”; a aceitação explícita de uma oferta v4 equivale a aplicar o mapa apresentado. Abrir, observar e preparar não criam nem migram layout.
- “Caminhos e EDID não viajam na rede”; não entram em logs, JSON de controle, oferta ou diagnóstico exportado.
- “Cache permite preparar rascunho; aplicar exige inventários observados nas conexões atuais.” Estimativa DRM não habilita aplicar.
- “canvas mantém o limite atual de ±1.000.000”; dead corners continuam `0..=32`, padrão `8`; `MAX_ZONES=16`, `MAX_LAYOUT_LINKS=64`.
- “protocolo v4, mínimo de conexão ainda 1”; variantes novas somente ao final de `InputMsg`. Nenhuma variante antiga recebe campo ou muda bytes.
- “cada sessão oferece uma ou duas saídas”; nenhum destino/rota arbitrário enviado pelo receptor é executado.
- “organização salva, ativação não confirmada” distingue persistência concluída de rearmamento não comprovado; não repetir a escrita automaticamente.
- “Trava manual continua impedindo saída.” Preservar o comportamento S9 atual: a trava cancela a captura remota, fecha sessão e impede nova abertura; não acrescentar recaptura de eventos injetados.
- Coordenadas nativas assinadas: físicas no Windows, lógicas no GNOME. Dimensões virtuais Windows dividem largura/altura por escala; origens nativas nunca são divididas individualmente pelo DPI.
- Origem notebook, retorno posicionado Linux e divisórias internas Linux multitelas continuam indisponíveis com causa. Não investigar o incidente de teclado adiado.
- Preservar S9 §§15.2–15.3 e §§15.13–15.14: autoridade independente das filas; liberação antes de rede; prazos totais de `2.000 ms`; buffer de abertura `256`; frontier por stream/conexão; pausa, revogação e retorno tardio não ressuscitam sessão.
- Sem dependência nova de terceiros: para EDID usar `sha2.workspace = true`, já fixada no workspace; atualizar o lockfile somente se necessário. UID usa aleatoriedade já disponível via `EventId::random()`.
- Unsafe somente em `clipsync-win/src/ffi.rs`, caso necessário; a coleta existente já entrega `Monitor.path`. Nenhuma ampliação de capability Tauri, grant, hook ou permissão de sistema.
- Texto português; sem `innerHTML`, estilo inline, script inline ou uso de dados remotos como seletor não escapado. UI só por `Ui::call`/`clipsync://event`.
- Maestro controla runtime, portais, contrato, liberação e release. Não usar Playwright nem equivalente. Nenhuma execução deste plano toca o perfil habitual do usuário.

## Foco da revisão

1. Dois monitores com mesmo nome e reconexão em ordem distinta: identidade por evidência, nunca renumerar links; testes T1/T3.
2. Falha entre backup, rename e ativação, concorrendo com edição avançada: nenhuma metade de mapa e nenhum rollback fictício; testes T1/T3/T4.
3. DPI fracionário, origem negativa e interseção que desaparece em `f32`: prévia e runtime concordam ou recusam; testes T1/T3.
4. `GetZones` negado, inventário mudando durante await, receptor sem layout: manter rascunho/legado e não criar captura/permissão; testes T3/T4.
5. Retorno antigo após revogar/reautorizar, troca de conexão e fila cheia: nenhuma tela errada ou estado pressionado retido; testes T2/T3 e gate T5.

## Task 1: identidade privada, documento v2 e compilador de organização

**Arquivos de teste:** criar `crates/clipsync-input/tests/s10_layout.rs` e `s10_identities.rs`; testes unitários junto a `layout_geometry.rs` para helpers privados. Manter os testes legados de `layout.rs`.

**Interfaces produzidas em `clipsync-proto::monitors`:**

```rust
pub struct MonitorUid(pub [u8; 16]); // Copy/Eq/Hash/Ord; JSON/TOML: 32 hex; wire: 16 bytes
pub enum CoordinateSpace { Physical, Logical }
pub enum GeometrySource { Observed, Estimated }
pub struct NativeRect { pub x: i32, pub y: i32, pub width: u32, pub height: u32 }
pub struct MonitorInfo {
    pub uid: MonitorUid, pub label: String, pub rect: NativeRect, pub scale: f64,
}
pub struct MonitorCapabilities {
    pub internal_edges: bool, pub positioned_return: bool, pub route_receiver: bool,
}
pub struct MonitorInventory {
    pub rev: u64, pub space: CoordinateSpace, pub source: GeometrySource,
    pub capabilities: MonitorCapabilities, pub monitors: Vec<MonitorInfo>,
}
pub struct MonitorKey { pub peer: PeerId, pub uid: MonitorUid }
pub struct MonitorPosition { pub key: MonitorKey, pub x: f64, pub y: f64 }
pub struct MonitorEndpoint {
    pub key: MonitorKey, pub edge: Edge, pub from: f32, pub to: f32,
}
pub struct MonitorLink { pub id: String, pub a: MonitorEndpoint, pub b: MonitorEndpoint }
```

`MonitorUid::random() -> MonitorUid`, `to_hex(self) -> String` e `from_hex(&str) -> Result<MonitorUid, WireError>` são as únicas conversões. Valor zero é inválido. Estes tipos são dados, sem I/O. Validação de wire e os limites de coleções chegam em T2; o compilador T1 já valida dados locais e não aceita valor não finito, dimensão zero, escala não positiva ou overflow. Inventário confirmado tem revisão não zero.

**Interfaces produzidas em `clipsync-input`:**

- `monitor_identities::Evidence::{WindowsPath(String), LinuxSingle { connector: String, edid_sha256: Option<[u8;32]> }}` nunca implementa `Serialize` para o wire nem `Debug` que revele evidência. Persistência usa representação privada própria.
- `Observation { evidence: Evidence, label: String, rect: NativeRect, scale: f64, legacy_aliases: Vec<String> }`; aliases são apenas candidatos de migração, não chave de identidade.
- `IdentityStore::new(profile: &Path) -> IdentityStore`; `reconcile(&self, observations: &[Observation]) -> Result<IdentifiedSnapshot, IdentityError>`, com `IdentifiedSnapshot { rev: u64, monitors: Vec<MonitorInfo>, aliases: Vec<IdentifiedAlias> }` e `IdentifiedAlias { alias: String, uid: MonitorUid }`. `IdentityError` distingue `Ambiguous`, `Unavailable`, `UnsupportedVersion`, `Busy`, `Io`, sem incluir path/EDID no texto exportável.
- `LegacyBinding { peer: PeerId, alias: String, uid: MonitorUid }`; o produtor local acrescenta seu peer ao `IdentifiedAlias`. Mudança/duplicidade de evidência recusa a correspondência, não reaproveita UID de registro anterior. Alias remoto só resolve por binding já confirmado ou nome exato de um inventário observado com uma única tela; nome duplicado/índice/múltiplas telas sem binding fica não resolvido. Não transmitir evidência privada para tentar completar migração.
- `LayoutDocument { legacy: Layout, organization: Option<Organization> }`, `Organization { positions: Vec<MonitorPosition>, links: Vec<MonitorLink>, legacy_bindings: Vec<LegacyBinding> }`. Ausência de `organization` significa formato v1; presença significa v2, mesmo se a lista de posições estiver vazia.
- `LayoutDocument::{read(&Path) -> Result<Option<Self>, LayoutError>, from_toml_str(&str) -> Result<Self, LayoutError>, to_toml_string(&self) -> Result<String, LayoutError>}`. `Layout`, `Link` e `Endpoint` legados conservam suas estruturas, evitando contaminar cada uso antigo com UID opcional.
- `LayoutStorage::new(profile: &Path) -> LayoutStorage`; `try_lock(&self) -> Result<LayoutGuard, LayoutError>`; no guard: `read()`, `write(&LayoutDocument) -> Result<(), LayoutError>`, `restore_v1(base_rev: u64) -> Result<u64, LayoutError>`. `read()` retorna o mesmo tipo de `LayoutDocument::read`. Todos os escritores usarão este guard em T3/T4.
- `InventoryView { peer: PeerId, inventory: MonitorInventory, aliases: Vec<LegacyBinding> }`; `OrganizationDraft { positions: Vec<MonitorPosition>, replace_link_ids: Vec<String> }` em `layout_geometry`.
- `compile_organization(current: &LayoutDocument, draft: &OrganizationDraft, inventories: &[InventoryView]) -> Result<CompiledOrganization, OrganizationError>`; `CompiledOrganization { document: LayoutDocument, effective_links: Vec<MonitorLink>, preserved_link_ids: Vec<String>, replaced_link_ids: Vec<String>, unresolved_link_ids: Vec<String> }`. `OrganizationError` contém código estável `invalid_geometry`, `monitor_missing`, `identity_ambiguous`, `segment_overlap`, `empty_segment`, `unsupported_topology` ou `advanced_link_conflict`.

O TOML v2 mantém as tabelas v1 (`device`, `link`, `options`, `rev`) e acrescenta `monitor_position`, `monitor_link`, `legacy_binding`; cada endpoint novo contém `peer`, `monitor_uid`, `edge`, `from`, `to`. Estes nomes e o `version=2` são fixos. O registro é `monitor-identities.toml`, `version=1`, com `rev` e entradas privadas de UID/evidência; não contém posições, links, permissões ou identidade do computador. O draft deste recorte nomeia duas ou três telas de exatamente dois peers (uma ou duas telas da origem Windows e uma do receptor); o compilador mescla posições por chave e preserva posições/links fora desse par. Uma terceira máquina não entra na compilação desta jornada.

Precisão de integração: `replace_link_ids` deve ser o conjunto exato, sem duplicatas, dos links já geridos que serão recompilados no par selecionado; omissão não permite apagar um link. IDs avançados ou de outro par recusam com `advanced_link_conflict`. Na primeira migração, sem geridos, a lista é vazia; adoções inequívocas idênticas do legado são explicitadas em `replaced_link_ids` da prévia confirmada por Aplicar. T4 deve montar o request com esse mesmo conjunto e conservar o `base_rev`.

Precisão de identidade dos links: IDs novos geridos são SHA-256 em 64 hex de endpoints canônicos com separação de domínio; inverter a ordem não altera o ID. Colisão com ID preservado recusa, sem sobrescrever. Não impor esse formato a IDs legados adotados. Um link legado com qualquer endpoint não resolvido permanece persistido e inativo, listado em `unresolved_link_ids` da prévia; só ambos resolvidos participam de conflito/adoção. T3 revalida resolução e conflitos antes de reativação; T4 mostra essas ligações inativas antes do aceite, sem dizer que preservadas significa ativas.

Precisão pós-revisão T1: falha ANTES de rename preserva o arquivo anterior; falha de sincronização do diretório DEPOIS do rename informa `LayoutError::PublishedUnconfirmed { rev: u64 }`, código `published_unconfirmed`, tanto em write quanto restore. A revisão publicada é conhecida, a durabilidade não. Não fazer rollback ou retry automático. T3 mantém passagens suspensas e devolve `OrganizationApplied` com `activation=Unconfirmed` e `durability=Unconfirmed`; T4 apresenta esse estado sem afirmar confirmação de gravação durável. Registro de identidades também distingue internamente publicação, mas não anuncia snapshot/UID em falha de confirmação. Falhas injetadas antes/depois de rename precisam observar bytes e estados reais.

## Task 3: inventário real, sessões com duas saídas e aplicação no agente
